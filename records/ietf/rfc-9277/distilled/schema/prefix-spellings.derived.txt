DERIVED - not verbatim. Not one byte string below is printed in
RFC 9277 except the two marked "THE ONE THE DOCUMENT PRINTS". Every
other line was enumerated for this record from RFC 8949 section 3's
head encodings, and none may be quoted as the source's own.

WHAT IT REFUTES, and it is the document's central claim. Section 2:
"Both use CBOR tags in a way that results in a deterministic first 8 to
12 bytes." (rfc-9277#R-0031) That is true only under PREFERRED
SERIALIZATION, and NOTHING IN RFC 9277 REQUIRES PREFERRED
SERIALIZATION -- because nothing in RFC 9277 requires anything: the
document has ZERO BCP 14 keywords. RFC 8949 section 3.1 admits a wider
head for the same argument value, and RFC 8949 section 4.1's preferred
rule is an ENCODER-side recommendation a conforming decoder does not
enforce.

So a well-formed, semantically identical file can begin with any of the
spellings below. A file(1) magic rule written from section 2.3.1's
"8 bytes d9d9f8da63740212 hex" matches 5 of the 30, and a rule written
from the 12-byte length matches 1 of the 30.

Section 2.1 DOES pin the tag NUMBER into 0x01000000..0xFFFFFFFF "In
order to be in the 4-byte range, and so that there are no leading zero
bytes in the 4-byte encoding of the tag number" (rfc-9277#R-0040). Note
exactly how far that goes: it constrains the VALUE and not the
ENCODING, so it forces `da` to be the SHORTEST head and does not forbid
`db`. And it is defeated outright on the OUTER tag, whose value is
55800 = 0xD9F8: spellings 11 to 30 below write that value in a 4- or
8-byte head and so put ZERO BYTES inside the first eight, which is the
very thing section 2.1 asks registrants to avoid "as these may confuse
implementations that treat the magic number as a C string"
(rfc-9277#R-0041).

PASS 2 (verify), 2026-10-20: RE-DERIVED, AND THE FLOOR SETTLED
---------------------------------------------------------------------
Both tables above were re-derived from RFC 8949 section 3 at pass 2
without reading them: for a tag, major type 6, the argument may be
written with additional information 24, 25, 26 or 27 whenever the value
fits, so 55800 = 0xD9F8 takes 3 spellings (d9, da, db -- ai 24 cannot
hold a 2-byte value) and TN(272) = 0x63740212 takes 2 (da, db); a 3-byte
byte string head takes 5 (43, 5803, 590003, 5a00000003,
5b0000000000000003). 3 x 2 x 5 = 30, and 3 x 2 = 6 for the wrapped
method. Every figure above reproduces, INCLUDING THE 25. Added at this
pass: 5 of the 6 wrapped-method spellings also put a zero byte inside
the first eight, which section 1 of this file does not state.

AND 30 IS NOT A FLOOR THAT COULD BE RAISED TO A TOTAL. Pass 1 called it
a floor and declined to enumerate the indefinite-length family. Settled
here: THE INDEFINITE-LENGTH FAMILY IS NOT FINITE. RFC 8949 section 3.2.3
defines an indefinite-length byte string as 0x5f followed by "zero or
more" definite-length byte strings and then 0xff, so an empty chunk
(0x40) is admissible and may be repeated without bound. Any number of
them may be inserted around the three content bytes and the decoded
value is unchanged, so the set of well-formed byte strings whose value
is 'BOR' is countably infinite, and so is the set of well-formed labels.
Two finite restrictions are worth having instead, because they are what
a magic rule would actually meet:
  * non-empty chunks, preferred chunk heads: the 4 compositions of 3
    (3 / 2+1 / 1+2 / 1+1+1), so 4 more per outer-inner pair = 24 more,
    for 54 in all;
  * non-empty chunks, any chunk head spelling: 5 + 25 + 25 + 125 = 180
    per pair = 1080 more.
None of them is 12 bytes and none matches the 8-byte fingerprint on its
own terms -- the fingerprint covers only the two tag heads, so every
indefinite spelling with the two shortest heads matches it as well,
which makes the fingerprint MORE permissive than the enumeration above
suggests rather than less. THE CONCLUSION IS UNCHANGED AND SHARPER: the
document's one deliverable is a byte prefix and the set of byte prefixes
that satisfy its own description is infinite.

WHAT THIS MEANS FOR US
---------------------------------------------------------------------
* As a DEFECT of the source: the document's single deliverable is a
  fixed byte prefix, and it leaves that prefix's own encoding to
  RFC 8949 section 4.2.1 by implication. It is the one place where this
  record touches the determinism work in draft-ietf-cbor-cde and
  draft-mcnally-deterministic-cbor, neither of which RFC 9277 cites.
* As a REQUIREMENT on anything of ours that reads such a file: accept
  the preferred spelling and reject the rest, or accept all of them.
  Accepting only the preferred one is the stricter and the safer
  reading, and the document gives no basis for either.
* As an argument about DEC-002: it is not an argument against option 5
  at all. Option 5 would not carry these tags, so it pays nothing here.
  What it shows is that THE SUBSTITUTE option 5 IS COMPARED AGAINST IS
  WEAKER THAN IT LOOKS -- "we could have had a magic number" is worth
  less when the magic number has 30 spellings and the specification
  that defines it requires nothing.
