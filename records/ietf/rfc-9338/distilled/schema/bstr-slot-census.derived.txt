rfc-9338 -- bstr-slot census of the eight permitted countersignature targets

DERIVED -- not verbatim.  Generated by this library, not printed anywhere in
RFC 9338.

WHY IT EXISTS.  RFC 9338 section 3.3 makes the whole of its repair turn on a
count it never performs: "other_fields: Omitted if there are only two bstr
fields in the target structure.  This field is an array of all bstr fields
after the second."  The `context` text string -- the only domain separator
between the version 1 and version 2 algorithms -- is "CounterSignatureV2" or
"CounterSignature0V2" only "when other_fields is present".  So which targets
get the version 2 signed bytes is arithmetic on RFC 9052's grammar, and the
document states the answer for exactly one structure, COSE_Sign1, as an
example.

HOW IT WAS DERIVED.  The member list of each structure, and the classification
of each member's type, are read out of
records/ietf/rfc-9052/distilled/schema/cose.cddl -- this library's VERBATIM
capture of RFC 9052's own CDDL -- by script, never typed from memory.  The
`Headers` group is inlined because every target structure opens with it.
`protected` is classified off the source's own rule
`empty_or_serialized_map = bstr .cbor header_map / bstr .size 0`, both of whose
branches are bstr.  Each member is printed with the optionality marker
cose.cddl gives it, so `? recipients` in COSE_recipient is `? recipients` here;
the marker changes no count, because an array member is not a bstr slot either
way, but a member list that drops it asserts something RFC 9052 does not.

THE COUNT IS BY TYPE SLOT, NOT BY WIRE ITEM, AND THE DOCUMENT'S OWN EXAMPLE
PROVES IT.  section 3.3 says other_fields "would be an array of one element for
the COSE_Sign1 structure containing the signature value".  COSE_Sign1 is
[protected, unprotected, payload : bstr / nil, signature : bstr].  That claim
holds only if `protected` is bstr field one and `payload : bstr / nil` is bstr
field two; drop either and COSE_Sign1 has two bstr fields, other_fields is
omitted, and the sentence is false.  Both columns are printed below so the
difference is visible: `slot-bstr` counts `bstr / nil` as a bstr, `wire-bstr`
does not.  THE TWO COLUMNS DISAGREE FOR SEVEN OF THE EIGHT STRUCTURES -- every
one except COSE_Signature, whose two bstr members are `protected` and
`signature` and neither of which can be nil, so it alone reads 2 and 2 -- and for
COSE_Sign1 the disagreement is exactly the detached-payload hazard: three slots
and two wire items, so an implementer who counts what arrived omits
other_fields and loses the signature binding silently.  RFC 9338 contains the
words `detach` and `nil` ZERO times.

THE RESULT, IN ONE LINE.  other_fields is present for COSE_Sign1, COSE_Mac and
COSE_Mac0 and absent for the other five, so five of the eight permitted targets
keep RFC 8152's context strings; and of the three that do get other_fields, it
carries a SIGNATURE for exactly one -- COSE_Sign1 -- and a MAC TAG for the other
two.  For COSE_Sign no signature value is reachable under any reading, because
`signatures : [+ COSE_Signature]` is an array and not a bstr field at all.
