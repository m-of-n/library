G-01  S  `id` CANNOT MATCH THE DOTTED SELECTORS THE DOCUMENT'S OWN
         EXAMPLES WRITE.  Appendix A: `id = ("$" / %x40-5a / "_" /
         %x61-7a) *("$" / %x30-39 / %x40-5a / "_" / %x61-7a)`.  The
         repeat set is $ 0-9 @ A-Z _ a-z.  It admits neither "-" (%x2D)
         nor "." (%x2E).  RFC 8610's own `id` does admit both: `id =
         EALPHA *(*("-" / ".") (EALPHA / DIGIT))`, `EALPHA = ALPHA / "@"
         / "_" / "$"` (verbatim from this library's
         records/ietf/rfc-8610/distilled/schema/cddl.abnf, lines 134 and
         136).  So Appendix A's `id` is STRICTLY NARROWER than the thing
         it selects from, and two consequences follow.
           (a) The document's own §2.6 examples are ungrammatical.  Source
               line 388: ";# include cose.label, cose.values from rfc9052
               as cose".  Source line 414: ";# import
               cose.empty_or_serialized_map from rfc9052 as cose".  Three
               dotted selectors, in TWO of the SEVEN directive instances
               the document prints (lines 311, 343, 375, 388, 414, 441,
               485).  Neither line is derivable from `directive`.
           (b) No rule whose name contains a hyphen or a dot can be named
               in a from-clause at all, although RFC 8610 admits such
               names and real models use them.
         Requirement ids: R-0082 (the production), R-0057 and R-0064 (the
         examples).  REPORTED, NOT REPAIRED.

G-02  S  `CRLF` IS REDEFINED AGAINST ITS OWN METALANGUAGE.  Appendix A
         declares the metalanguage to be "the ABNF language defined in
         [STD68] and [RFC7405]" (R-0077).  STD 68 (RFC 5234) defines the
         core rule CRLF = CR LF.  Appendix A redefines it: `CRLF = %x0A /
         %x0D.0A` (R-0087), admitting a BARE LF.  This is the same
         redefinition RFC 8610 Appendix B makes - defect 7 in this
         library's rfc-8610 record - but there it is camouflaged by
         identical redefinitions of ALPHA, DIGIT, HEXDIG and SP, whereas
         here only `SP = %x20` (R-0086) keeps its core value, so this one
         redefinition stands alone and unremarked.  Practical effect: the
         grammar is correct for Unix text files and silently disagrees
         with STD 68 about what terminates a directive.

G-03  S  THE PROSE AND THE GRAMMAR DISAGREE ON WHAT MAKES A LINE A
         DIRECTIVE.  §2.3: "In the CDDL module structure, lines that
         start with the prefix ;# are parsed as directives" (R-0033).
         Appendix A: `directive = ";#" RS ...` with `RS = 1*WS` (R-0078,
         R-0084) - whitespace after ";#" is REQUIRED.  So ";#import
         rfc9052" is a directive under the prose and not under the
         grammar.  Worse in the other direction: a plain basic-CDDL
         comment that happens to begin ";#" - a section banner, a
         machine-readable annotation of some other convention - is a
         directive under the prose and ungrammatical under Appendix A,
         and the document nowhere says whether a processor must then
         raise an error or fall back to treating the line as the comment
         it also is.  That choice is the whole of the compatibility
         story and it is not made.

G-04  N  THE FROM-CLAUSE IS AMBIGUOUS WHEN A SELECTED RULE IS NAMED
         `from`.  `from-clause = 1*(id-or-all [","] RS) %s"from" RS`
         (R-0079), and `from` is matched by `id`.  ";# include from from
         rfc9052" is in the language twice over.  ABNF defines a language
         rather than a parse, so this is not a defect in the grammar; it
         is a disambiguation an implementer must invent.  Note also that
         the comma is OPTIONAL and the required separator is whitespace,
         so ";# include label values from rfc9052" is grammatical and
         selects two rules.

G-05  S  A DIRECTIVE MUST BEGIN IN COLUMN 1.  `directive` starts with the
         literal ";#" and admits no leading `RS` (R-0078).  RFC 8610
         comments may be indented freely, so an indented ";# import m" is
         a comment to every tool, including a module-structure processor.
         §2.3's "lines that start with the prefix ;#" (R-0033) does not
         say whether leading whitespace is permitted.  Anyone laying out
         a module file with indented blocks has to know this and the
         document does not tell them.

G-06  S  A DIRECTIVE ON AN UNTERMINATED FINAL LINE IS NOT A DIRECTIVE.
         `directive` ends in `CRLF` (R-0078), so a file whose last line
         is ";# import m" with no trailing newline contains no directive.
         Nothing says so, and the failure is silent: the line is still a
         valid basic-CDDL comment, so the file still parses and the
         import simply does not happen.

G-07  S  NO TRAILING SPACE AND NO TRAILING COMMENT.  `directive` runs
         `filename [as-clause] CRLF` with no `[RS]` before the
         terminator (R-0078), so ";# import rfc9052 " - one trailing
         space - is not a directive, and there is no way to put a remark
         on a directive line.  Same silent-failure shape as G-06.

G-08  S  MODULE NAMES ARE FLAT: THERE IS NO HIERARCHY AND NO PATH.
         `filename = 1*("-" / "." / %x30-39 / %x41-5a / "_" / %x61-7a)`
         (R-0081) admits no "/" and no other separator.  A module name is
         one unqualified token resolved against a search path (R-0034),
         whose precedence between directories is "intentionally not fully
         defined" (R-0036).  Consequence, which §3 states in its own
         words: the same module name resolves to different bytes in
         different environments, and "the possibility of supply-chain
         attacks on the modules imported needs to be considered"
         (R-0072).

G-09  S  "." , ".." AND "-" ARE GRAMMATICAL MODULE NAMES.  `filename`
         (R-0081) admits any non-empty string over - . 0-9 A-Z _ a-z,
         with no exclusion of the two directory names every filesystem
         reserves, and none of a leading "-", which every command-line
         search path treats as an option.  ";# import .." is a legal
         directive.

G-10  S  THE OUTPUT NAME SPACE USES A CHARACTER THE DIRECTIVE GRAMMAR
         CANNOT READ BACK.  An `as` prefix is a single `id` (R-0080),
         which by G-01 cannot contain a dot; yet the names the mechanism
         EMITS are dotted - "cose.COSE_Key", "cose.label",
         "cose.Generic_Headers" (source lines 348, 356, 427).  So the
         composed output cannot be re-selected by a directive, prefixes
         cannot nest, and a second-level namespacing of an
         already-prefixed module has no spelling.  Combined with G-01(a)
         this is one defect seen from two sides: the prefixed name is
         simultaneously what the document writes in its own from-clauses
         and what its own `id` production forbids there.

G-11  N  NO CONFLICT RULE FOR TWO AS CLAUSES, OR FOR A PREFIX THAT
         COLLIDES WITH A LOCAL NAME.  Nothing in the grammar or the prose
         prevents one module writing ";# import a as x" and ";# import b
         as x", nor a module defining "x.y" itself and then importing
         something "as x".  The only rule in force is RFC 8610's, which
         this document restates as fact: concatenation "creates a valid
         CDDL data model unless there is a name collision (_identical_
         redefinition is allowed to facilitate this approach)" (R-0015).
         So a prefix collision is a name collision with no diagnostic
         specified - exactly the failure the `as` clause exists to
         prevent, relocated one level up.

G-12  N  THE ORDER IN WHICH COMPOSED RULES ARE EMITTED IS NOT SPECIFIED,
         AND THAT ORDER IS SEMANTIC.  The word "order" occurs ONCE in the
         whole document (source line 181, "in order to obtain the desired
         data model") and is not about output order; "precedence" occurs
         once (line 252) and is explicitly left undefined (R-0036);
         "determined" occurs once (line 259), about the tool's set of
         source directories.  The seven printed outputs
         are all CONSISTENT with "the importing module's own rules first,
         then the selected rules, then their closure" - but that is
         induction from seven examples, not a rule.  It matters because
         RFC 8610 §2.2.2 and §3.9 make an accretive choice "populated in
         the order the rules are given" (rfc-8610#R-0102), so for any
         model that uses "/=" or "//=" the emission order changes the
         language.  The strings "/=" and "//=" occur ZERO times in this
         document.

G-13  N  WHETHER AN AS CLAUSE PREFIXES A SOCKET NAME IS NOT STATED, AND
         EITHER ANSWER BREAKS SOMETHING.  "socket", "plug" and "$$" occur
         ZERO times in the document.  §2.2 says the prefix is prepended
         to "the names of rules being imported" (R-0028), without
         exception; §2.5's only stated exception is the CDDL prelude
         (R-0053).  Appendix A's `id` admits "$" in every position
         (R-0082), so a socket IS selectable in a from-clause.  Two
         readings, both bad:
           (a) sockets ARE prefixed.  Then "$$ext" becomes "cose.$$ext"
               and a plug written elsewhere as "$$ext /= ..." no longer
               plugs it: importing a module silently disconnects its
               extension point.
           (b) sockets are NOT prefixed.  Then the one construct RFC 8610
               offers as a registry-free extension point keeps a flat
               global name across every module in the build, and the
               collision the module structure exists to prevent persists
               for precisely that construct.
         The document chooses neither.  See ../design-notes.md,
         *Does module naming fix the socket collision?*

G-14  N  THE PRELUDE EXEMPTION IS A SIDE CONDITION NO PRODUCTION CARRIES,
         AND IT IS STATED BY EXAMPLE.  R-0053: imported names are
         prefixed "but CDDL prelude (Appendix D of [RFC8610]) names such
         as tstr and any are not".  "Such as" - the exempt set is the
         whole of RFC 8610 Appendix D, 40 rules, incorporated by
         reference.  A conforming processor therefore needs the prelude as
         DATA, and a processor built against a later prelude would prefix
         a different set of names than one built against RFC 8610's.  The
         prelude "is deemed to be fixed" per RFC 8610, which is what makes
         this workable, and nothing here says so.

G-15  N  THE WILD-CARD IS ADMITTED AND NEVER EXERCISED.  `id-or-all = id
         / "*"` (R-0083) and §2.6's opening sentence offers "a wild-card
         "*" for all rules" (R-0054).  No example in the document uses
         it, and no sentence says how ";# include * from m" differs from
         ";# include m", or what ";# import * from m" means given that
         import's whole definition is reachability from the importing
         module (R-0047).

G-16  S  THERE IS NO EXPORT DECLARATION, AND INCLUDE REACHES THROUGH A
         MODULE INTO ITS DEPENDENCIES.  "export", "public", "private" and
         "visible" occur ZERO times in the document outside the copyright
         boilerplate.  R-0046 defines include as drawing in "all the
         rules from a module (which includes the ones imported/included
         there, transitively)".  Two consequences: a module cannot make
         any rule private, and ADDING AN IMPORT TO A MODULE CHANGES WHAT
         ITS CONSUMERS' `include` DRAWS IN - a non-local effect with no
         declaration anywhere to constrain it.  All selection is on the
         consumer side (R-0046, R-0047, R-0054); the producer declares
         nothing.  Counts, exactly: "export", "private" and "visib" occur
         ZERO times; "public" occurs ONCE, inside "date of publication"
         in the copyright boilerplate (line 80).

G-17  I  COMPOSITION DESTROYS EVERY COMMENT, INCLUDING THE DIRECTIVES.
         Observable in the document alone: the seven composed outputs it
         prints (source lines 315-325, 347-357, 379-381, 399-401,
         420-435, 455-471, 509-519) contain NOT ONE ";" character.  The
         only semicolons in the whole example region are the ";#" of the
         seven INPUT directives.  Since directives are comments (R-0023,
         R-0032) and the output is basic CDDL with no directives, the
         transformation is ONE-WAY: a composed model cannot be read back
         as the module structure that produced it.  And since RFC 8610
         §3.1 puts everything a schema says about MEANING in comments,
         whatever documentation a module carries there does not survive
         the build.  The document never says either.  The cross-document
         half of this - that the RFC 9052 fragments these outputs are
         drawn from do carry such comments ("; kty", "; kid", "; alg",
         "; criticality") - rests on this library's verbatim capture at
         records/ietf/rfc-9052/distilled/schema/cose.cddl lines 60-67 and
         168-175, not on this source, and is attributed there.

G-18  N  `$.start.$` IS USED ONCE AND NEVER DEFINED.  Source line 509,
         the §2.7 output: "$.start.$ = cose.COSE_Key" (R-0068).  The name
         occurs exactly once in the document.  It is a valid RFC 8610 `id`
         - and it is spelled like an RFC 8610 §3.9 TYPE SOCKET, because
         it begins with "$" - yet it is defined with "=" where §3.9's
         sockets are extended with "/=".  No sentence introduces the
         convention, says whether the name is reserved, or says what a
         basic-CDDL tool should make of a socket-shaped root rule.

G-19  -  NOT A DEFECT, RECORDED SO IT IS NOT "FIXED": `id` admits "@"
         (its first and repeat sets both start at %x40) where `filename`
         does not (%x41-5a).  That one-codepoint difference is CORRECT:
         RFC 8610's EALPHA includes "@", so a rule name may contain it,
         and a filename has no such need.  R-0081, R-0082.

G-20  -  TOOL-INTERFACE INCONSISTENCY, informative only.  Every example
         in §2.5-§2.7 writes the conversion flags as one argument,
         "cddlc -2tcddl -" (source lines 309, 341, 373, 386, 412, 439,
         481).  Appendix B writes them as two, "cddlc -2 -tcddl
         mytestfile.cddl" (line 701, R-0090).  Appendix B is declared
         "for information only" (R-0088), so neither spelling is
         normative; recorded because anyone reproducing the vectors will
         hit it.

G-21  N  WHICH SPELLING OF A SELECTED NAME PRODUCES AN UNPREFIXED ALIAS
         IS SHOWN BY EXAMPLE ONLY.  Compare two directives that differ in
         one respect:
           line 414  ";# import cose.empty_or_serialized_map from rfc9052 as cose"
                     -> output has NO alias rule (lines 420-435)
           line 441  ";# import empty_or_serialized_map from rfc9052 as cose"
                     -> output HAS "empty_or_serialized_map =
                        cose.empty_or_serialized_map" (line 456)
         So writing the selector in its post-prefix spelling selects it,
         and writing it in its pre-prefix spelling selects it AND emits an
         alias.  R-0064 points the difference out ("Note how an additional
         rule provides an alias") without stating it as a rule.  The
         `include` counterpart is shown only in the post-prefix spelling
         (line 388, no alias at lines 399-401); the pre-prefix `include`
         with an `as` clause is never shown and its behaviour is unknown.
         Note that by G-01 the post-prefix spelling is the one Appendix
         A's `id` cannot even match.
