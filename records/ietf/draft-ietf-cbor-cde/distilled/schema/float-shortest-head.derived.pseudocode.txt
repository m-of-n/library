draft-ietf-cbor-cde — shortest-head for IEEE 754 floating point
==============================================================

0.  WHAT CDE ADDS, AND DOES NOT ADD
-----------------------------------
[Section 3.1.2]

  CDE defines NO float rule of its own.  "To obtain the CBOR Common
  Deterministic Encoding (CDE), this specification entirely recurs to the
  shortest-head component of Preferred Serialization and does _not_ itself
  define any additional constraints."  Everything below is shortest-head
  applied to major type 7, plus the five clarifications Section 3.1.2 adds
  "in the order of the bullet list at the end of Section 4.2.2 of RFC 8949":

   1. Zeros: no special action.  "an encoder that is asked by an
      application to represent a negative floating point zero (-0.0) will
      generate 0xf98000."
   2. No integer/float mixing.  "all floating point values are encoded as
      the preferred floating-point representation that accurately
      represents the value, independent of whether the floating point
      value is, mathematically, an integral value".
   3. NaNs: "there is no special handling of NaN values, except a
      clarification that the Preferred Serialization rules also apply to
      NaNs (with zero or non-zero payloads)".
   4. "There is no special handling of subnormal values."
   5. "CDE does not presume equivalence of basic floating point values
      with floating point values using other representations (e.g., tag
      4/5)."

  The consequence the document spells out, and the one applications trip
  over: "This means that the application has no control over the
  representation size, e.g., the number 1.0 will always be serialized as a
  binary16 floating point number (0xf93c00) as that is the shortest
  representation that preserves the value." [Section 3.1.2]


1.  THE CASCADE
---------------
[Appendix C.1.1 item 2: "If multiple of these encodings preserve the
precision of the value to be encoded, only the shortest form of these MUST
be emitted.  That is, encoders MUST support half-precision and
single-precision floating point."]

  FUNCTION cde_encode_float(v) -> bytes
      ; v is the application's value, taken as an IEEE 754 interchange bit
      ; pattern widened to binary64 or wider.
      IF representable_as(v, binary16):  RETURN [0xf9] || b16(v)   ; ai 0x19
      IF representable_as(v, binary32):  RETURN [0xfa] || b32(v)   ; ai 0x1a
      RETURN [0xfb] || b64(v)                                      ; ai 0x1b
      ; "The length of the argument indicates half (binary16, ai = 0x19),
      ;  single (binary32, ai = 0x1a) and double (binary64, ai = 0x1b)
      ;  precision encoding." [C.1.1 item 2]

  THE ORDER IS THE WHOLE RULE: try f16 first, then f32, then f64.  Note
  that try-float16-encode.c -- the document's own code -- implements only
  the first test, and the document supplies NO binary64 -> binary32
  counterpart.  An implementer who takes Appendix F as the float encoder
  has two thirds of a cascade.  Appendix F is explicit that it is giving
  only the f16 leg, but it is the only code in the document, and 17 of
  Table 5's 63 rows answer fa... -- rows Appendix F cannot produce at all.

  binary128 and wider are out of scope: CBOR has no head for them, and an
  application presenting one must reduce it to binary64 or below before
  encoding.  The document does not discuss this.


2.  REPRESENTABLE_AS, BY VALUE CLASS
------------------------------------

  Trailing-significand widths and the derived NaN payload widths.  The
  payload is "All but the first bit (Q-bit) of the trailing significand
  component of the [IEEE754] value for a NaN.  Separate from sign bit and
  Q-bit." [Section 1.2]

      format     exponent bits   trailing significand   NaN payload
      binary16         5                 10                   9
      binary32         8                 23                  22
      binary64        11                 52                  51

  FUNCTION representable_as(v, F) -> bool
      SWITCH class(v):

      CASE zero:                                   ; [3.1.2 item 1]
          RETURN F == binary16
          ; "Positive and negative infinity and zero MUST be represented in
          ;  half-precision floating point." [C.1.1 item 2]
          ; +0.0 -> f90000, -0.0 -> f98000.  The sign is preserved and is
          ; NOT normalised away; -0.0 and 0.0 are distinct encodings, which
          ; is what makes the RFC 8949 Section 5.6.1 map-key equivalence a
          ; separate check (see cde-encode...txt section 4.2).

      CASE infinity:                               ; [C.1.1 item 2]
          RETURN F == binary16
          ; +Inf -> f97c00, -Inf -> f9fc00.

      CASE nan:                                    ; [3.1.2 item 3]
          RETURN nan_fits(v, F)                    ; section 3 below

      CASE finite nonzero:
          RETURN narrow(v, F) widens back to exactly v
          ; "floating point values are represented with the shortest head
          ;  [...] that preserves the value of the data item"
          ;  [Section 3.1.2].  Exact round-trip, nothing else: no
          ;  tolerance, no shortest-decimal-that-round-trips (that is
          ;  JSON's problem, not CBOR's).
          ; SUBNORMAL TARGETS ARE FINE.  "There is no special handling of
          ; subnormal values" [3.1.2 item 4] cuts both ways: a value that
          ; is exactly a binary16 subnormal IS encoded as binary16.
          ; Table 5's first such row is 5.960464477539063e-8 -> f90001,
          ; "Smallest positive f16 (subnormal)".


3.  NaN NARROWING — THE PAYLOAD-TRIMMING RULE
---------------------------------------------
[Appendix C.1.1 item 2, third bullet, quoted in full:]

  "For NaNs, the value to be preserved includes the sign bit, the quiet
   bit, and the NaN payload (whether zero or non-zero).  The shortest form
   is obtained by removing the rightmost N bits of the payload, where N is
   the difference in the number of bits in the significand (mantissa
   representation) between the original format and the shortest format.
   This trimming is performed only (preserves the value only) if all the
   rightmost bits removed are zero.  (This means that a double or single
   quiet NaN that has a zero NaN payload will always be represented in a
   half-precision quiet NaN.)"

[and Section 3.1.2 item 3:]

  "shorter forms of encodings for a NaN are used when that can be achieved
   by only removing trailing zeros in the NaN payload"
  "the CBOR encoding always uses a leading bit of 1 in the significand to
   encode a quiet NaN; the use of signaling NaNs by application protocols
   is NOT RECOMMENDED but when presented by an application these are
   encoded by using a leading significand bit of 0."

  FUNCTION nan_fits(v, F) -> bool
      N = significand_bits(format_of(v)) - significand_bits(F)
      IF N < 0:  RETURN false                  ; never widen
      RETURN (payload(v) AND ((1 << N) - 1)) == 0

  FUNCTION nan_narrow(v, F) -> bit pattern in F
      N = significand_bits(format_of(v)) - significand_bits(F)
      sign    = sign_bit(v)                    ; preserved
      quiet   = leading_significand_bit(v)     ; preserved: 1 = qNaN, 0 = sNaN
      payload = payload(v) >> N                ; trimmed, trailing zeros only
      RETURN  (sign    << (exponent_bits(F) + significand_bits(F)))
            | (all_ones(exponent_bits(F)) << significand_bits(F))
            | (quiet   << (significand_bits(F) - 1))
            | payload

  N for each leg, from the table in section 2:
      binary64 -> binary32:  N = 52 - 23 = 29
      binary64 -> binary16:  N = 52 - 10 = 42
      binary32 -> binary16:  N = 23 - 10 = 13

  Note that N is the difference in SIGNIFICAND widths (52/23/10), while the
  bits being shifted are the PAYLOAD (51/22/9).  Those differ by exactly
  one -- the quiet bit -- in every format, so the shift lands the payload
  correctly.  Section 1.2's definition of "NaN payload" is what makes this
  come out right, and the easy error is to shift the whole trailing
  significand instead, which loses the quiet bit on every narrowing.

  THE TRIVIAL NaN.  "A NaN with a zero sign bit, and a payload composed of
  zero bits only. [...] Represented in CDE as the three bytes 0xf97e00."
  [Section 1.2]  And: "Typically, most applications that employ NaNs in
  their storage and communication interfaces will only use a single NaN
  value: quiet, non-negative NaN with a payload of all zero bits.  This
  value therefore deterministically encodes as 0xf97e00." [Section 3.1.2]
  An implementation whose application never produces another NaN need
  implement no NaN narrowing at all -- Section 3.1.2 says so: "a CDE
  implementation focusing on this application would not even need to
  provide processing for other NaN values."

  SIGNALING NaNs SURVIVE.  The rule preserves the quiet bit rather than
  quieting the value, so a signaling NaN handed to the encoder is encoded
  as a signaling NaN.  That is deliberate (Section 3.1.2 item 3, quoted
  above) and is why 9 of Table 5's 20 NaN rows are signaling NaNs.  The
  document nonetheless marks their use NOT RECOMMENDED.  (One of those 9
  comments is misspelled "sNan" in the source, at cached source line 1950.)

  THE DECODER-SIDE INVERSE, for getpayload/setpayload users
  [Section 3.1.2, closing aside]: "A good way to handle this diversity is,
  upon decoding, to widen the representation size of all NaNs to a common
  size, often double precision ([IEEE754] binary64), before applying
  getpayload/setpayload.  The inverse to the narrowing performed by
  preferred serialization, this widening operation successively adds the
  necessary one bits to the exponent and trailing zero bits to the payload
  to build the next longer form until the desired size for the NaN has been
  reached."


4.  WHAT IS NOT CONSTRAINED HERE
--------------------------------

  - Where the float came from.  "A particularly difficult field to obtain
    deterministic encoding for is floating point numbers, partially
    because they themselves are often obtained from processes that are not
    entirely deterministic between platforms." [Section 3.1.2]  CDE makes
    the ENCODING of a given value deterministic and says nothing about two
    platforms computing the same value.
  - Tag 4 / tag 5 (decimal fraction, bigfloat).  No equivalence is
    presumed [3.1.2 item 5]; 2.0, tag 4 [-1, 20] and tag 5 [1, 1] stay
    three distinct data items under CDE.  Collapsing them is an ALDR-level
    decision [Appendix B].
  - Whether an application may use floats at all.  "there is no
    requirement that implementations of that set of ALDR rules support
    floating point numbers (or any other kind of number ...)"
    [Appendix B].
  - What a decoder presents.  "generic decoders often will expand floating
    point numbers to a single size that is convenient on the platform
    (such as binary64)" [Section 3.1.2] -- so the encoded head length is
    not observable by the receiving application, and a CDE round trip is
    byte-stable but not head-stable through a generic decoder's API.
