# draft-ietf-vcon-vcon-core-04 — schemas

The draft ships **two schemas of its own**, and both are now held here byte for
byte. Until this pass the directory held only `types.derived.cddl`, 71 lines
generated by `bin/derive` from our own field table — the FX-1 *fallback* for a
source that has only prose, built for a source that has two formal schemas. The
fallback is kept, because it is what `fields.yaml` says and the disagreement
between it and the source is itself a finding, but it is no longer what a reader
should consult first.

## De-furnishing — the only transformation applied

Two edits, both mechanical, both re-derivable:

1. **Page furniture removed.** This draft's page frame is fixed at 48 body
   lines: 3 blank lines, the `Petrie ... [Page n]` footer, a U+000C form feed,
   the `Internet-Draft ... September 2026` running head, 2 blank lines. Exactly
   that 8-line block was deleted, 29 times in Appendix B and 8 times in
   Appendix C. Because the 3 trailing blanks are **fixed** padding and not
   variable fill, a blank line beyond them belongs to the body: four pages of
   Appendix C end on a real blank separator, and those four were kept. Appendix
   B's JSON contains no blank line at all, so the question does not arise there.
2. **Left margin removed.** Both appendices are printed with a uniform 3-column
   left margin. Three columns were removed from every line; the minimum
   indentation over all non-blank lines in each region is exactly 3, so nothing
   else moved. Relative indentation, inline `;` comments, column alignment and
   internal blank lines are untouched.

Nothing else was changed. `vcon.schema.json` was re-checked line by line against
the source range — 1379 of 1379 lines match after re-adding the margin, zero
mismatches. `types.cddl`'s header states the same digest this table does, and it
is the digest of the bytes between its markers.

`vcon.schema.json` carries no header: JSON has no comment syntax, so a header
would be the one thing the file must not contain. Its provenance lives here.

## Source defect — Appendix B is not valid JSON

**`vcon.schema.json` does not parse.** `json.load` fails at file line 5,
column 66 (source line 6746) with *"Invalid control character"*. It is not a
transcription fault and it has not been repaired here.

The appendix says what it did, at source lines 6737–6740:

> The JSON Schema definition below has been formatted with line breaks to print
> nicely on the page. The unformatted version of the JSON schema can be
> downloaded from: `https://raw.githubusercontent.com/ietf-wg-vcon/`
> `draft-ietf-vcon-vcon-core/refs/heads/main/vcon_json_schema.json`

Those line breaks fall **inside string literals**, which RFC 8259 §7 forbids: a
JSON string may not contain an unescaped U+000A. There are **89** of them, all
inside `description` (85) or `$comment` (4) values. The first:

```
6746 |     "description": "JSON schema for the unsigned form of vCon (Conv
6747 |       ersational Data Container) as defined in RFCXXXX",
```

**The wrapping is lossy, and that is the serious half of the defect.** Most
breaks fall mid-word and rejoin cleanly (`(Conv` + `ersational`). But **25 of
the 89 fall on a word boundary, and the space is simply gone** — it is in
neither line, and nothing in the text marks which breaks ate one:

```
6799 |     "description": "Last modified time of this vCon in RFC3339
6800 |       format",                                  -> "RFC3339format"
6827 |     "description": "HTTPS URL where the referenced vCon is
6828 |       stored",                                  -> "isstored"
6993 |     "description": "Decentralized Identifier (DID) URI for
6994 |       the party"                                -> "forthe party"
8338 |     "$comment": "The redacted and amended parameters are mutually
8339 |       exclusive"                                -> "mutuallyexclusive"
8350 |   ttachments parameters SHOULD be present (RFCXXXX Section 4).
8351 |   SHOULD-level statements are not enforced by this schema."
                                                       -> "4).SHOULD-level"
```

The last one has lost one space or two — RFC prose double-spaces after a period,
so even the *number* of lost characters is unrecoverable. Ten of the 25 leave a
footprint (their continuation line is indented 3 columns past the opening line
rather than 2), but the other fifteen do not, so there is no rule that recovers
them. **The annotation text of Appendix B cannot be reconstructed from the
document.** A reader who needs the prose of a `description` must fetch the
unformatted file the appendix links to, or read the numbered section it cites.

No key, `type`, `format`, `const`, `enum`, `pattern`, `$ref`, `required` or
conditional is affected. The schema's *meaning* survives the defect intact; only
its documentation strings do not.

### `vcon.derived.schema.json` — the parseable rendering

Because the verbatim file cannot be fed to a validator, this directory also
carries the mechanical repair, named `.derived.` as library#44 requires. Two
edits, and only two:

- each of the 89 string-internal line breaks, and the indentation run following
  it, deleted — **with no space inserted**, so the 25 run-together words above
  are present here too and must not be quoted as the draft's prose;
- `$id` rewritten from `https://ietf.org/vcon/schemas/unsigned-vcon.json` to
  `urn:library:draft-ietf-vcon-vcon-core-04:vcon-json-schema`, per the naming
  rule for a derived schema. The original value is recorded in this sentence and
  nowhere else in the file.

A third key, `x-library-derivation`, is prepended so the file states what it is
when it travels alone; JSON Schema draft-07 ignores unknown keywords. The pure
unwrap, before the `$id` rewrite and that key, is sha256
`63414c658efa8f618c9fbf8f7b6d9fcaa267cf1852d3e093d41c14945a6794b6`. It parses.
It is the unsigned form only, so of the record's nine `distilled/examples/`
files it is the applicable schema for seven; `a6-signed-vcon.json` and
`a7-encrypted-vcon.json` are the §5 forms that only `types.cddl` covers. No
validator was run against it in this pass — `jsonschema` is not installed here
— so *parses* is the whole of what has been checked.

## Appendix B and Appendix C are not equivalent

They are two schemas for one format, and they differ in both coverage and
strength. Neither fact is stated in the draft.

**Coverage.** Appendix B is titled *"vCon - Unsigned Form"* and its `$id` ends
`unsigned-vcon.json`: it describes §4 only. The signed (JWS, §5.2) and encrypted
(JWE, §5.3) forms are absent from it. Appendix C covers all three —
`vcon = unsigned_vcon_type / signed_vcon_type / encrypted_vcon_type` — and
defines `signature_object_type`, `signed_header_object_type`,
`unprotected_object_type`, `recipient_object_type` and
`recipient_header_object_type` for them. For §5, Appendix C is the only schema
the draft has.

**Strength on prohibitions.** Appendix C's own preamble, in the first lines of
`types.cddl`, disclaims them:

> Note: the extension parameter wildcard (`* tstr => any`) means the per-type
> parameter prohibitions in this CDDL are advisory; a prohibited parameter
> matches the wildcard. The prose and Table 1 of the draft are definitive.

That is exactly right, and it is the draft admitting that its CDDL cannot test
the thing §4.3.1.6 Table 1 is about. Appendix B does not have the same problem:
it writes the Table 1 prohibitions as `if`/`then`/`not`/`anyOf` over `required`,
which bites without closing the object. Its `Dialog` definition carries nine
conditionals — `incomplete` ⇒ `disposition`, `recording-set` ⇒ `recordings`,
non-empty `body` ⇒ `encoding` and `mediatype`, plus per-type prohibition lists
for `transfer` (13 parameters), `recording-set` (14), `incomplete` (15),
`recording` (7) and `text` (8). **For dialog-type prohibitions, Appendix B is
enforceable and Appendix C is not.**

**How much of Table 1 each one reaches.** The table is 24 parameters × 5 types =
120 cells: `X` 57, `O` 30, `S` 19, `M` 9, `SN` 4, `-` 1. Both appendices carry
`M` and `X` and neither carries `S`, `SN` or `-`, but they fail differently, and
the difference is where the two languages actually stop.

| | cells | Appendix B (JSON Schema draft-07) | Appendix C (CDDL) |
|---|---|---|---|
| `M` | 9 | 7 flat — `type` on all five via `Dialog.required`, `recordings`, `disposition`. The two `M (1)` `mediatype` cells become footnote 1's live conditional. | the same 7, as members without `?`. The two `M (1)` cells are **demoted** to `? mediatype` with the obligation moved into a comment. |
| `X` | 57 | **all 57**, exactly, as `not`/`anyOf`/`required`. Enforceable. | all 57, by omission from the branch. **Advisory** — the wildcard matches anything omitted. |
| `S` | 19 | none. Says so itself: *"SHOULD-level statements are not enforced by this schema."* | none as schema; several survive as `;` comments. |
| `SN` | 4 | none — and `disposition` appears in no prohibition list, so B keeps `SN` **distinct** from `X`. | **conflated with `X`**: omission is C's only encoding for both, so four cells the table distinguishes are indistinguishable here. |
| `O` | 30 | the default state, never a positive assertion. | `?`, likewise. |
| `-` | 1 | nothing at all. | nothing as schema, but the legend's sentence is preserved verbatim as a comment on the transfer branch. |

The reason is not a defect in either language. `M` and `X` are predicates over an
instance and both languages have them. `S` and `SN` are obligations on an author
with conforming instances on both sides, so no validator can decide them — a
schema's verdict is binary and `SHOULD` is a third value. `-` is a semantic void,
syntactically identical to `O`, so it is unrepresentable by construction and can
only travel as prose. The two places a schema language could have done better and
did not are Appendix C's demotion of `M (1)` and its conflation of `SN` with `X`;
both were expressible and neither was expressed.

## Structural validity is not conformance

This directory's two verbatim schemas independently confirm what the record's
own README concluded. Neither can be used as a conformance test:

- **Both are open-world by construction.** Appendix B sets
  `additionalProperties` nowhere — zero occurrences in 1379 lines — and
  Appendix C splices `extension_parameters_type = (* tstr => any)` into every
  map. That is correct, because §2.5 permits extension parameters anywhere; the
  consequence is that an unknown parameter is never an error in either. The
  record's `distilled/examples/a7-encrypted-vcon.json` shows the price: it
  carries a top-level `protected` parameter that neither §5.3 nor `types.cddl`
  defines, and `* tstr => any` accepts it without a word.
- **Neither expresses SHOULD.** Appendix B says so in its own top-level
  `$comment`: *"SHOULD-level statements are not enforced by this schema."*
  Appendix C says so in its preamble: *"Constraints that cannot be expressed in
  CDDL are stated in comments."* The record's requirement set, not these files,
  is where SHOULD-level obligations live.
- **Neither checks a cross-object index.** `parties`, `originator`, `dialog`,
  `attachment`, `recordings`, `original`, `consultation`, `target_dialog` and
  `transfer_target` are all `uint` / `integer, minimum 0`. That an index points
  at an object that exists is unexpressed in both.
- **Neither checks a value's internal syntax.** `content_hash`, media types,
  `gmlpos`, DID URIs and Base64Url strings are `tstr`/`string`. Appendix B adds
  `format: uuid` on `uuid`, `created_at` and `updated_at` only, and `format` is
  an annotation in draft-07, not an assertion. UUID version 8 (§4.1.2) is
  unexpressed in both.
- **Neither reaches §5's cryptography.** That `signature` verifies, that
  `content_hash` matches the bytes at `url`, that `x5c` chains — none of it is
  schema-shaped.

Both appendices put this plainly themselves, in near-identical words. Appendix B
(source 6729–6734), and Appendix C in the same form:

> This JSON schema is provided as informational. The text in sections 1-6 of
> this document define the normative definition of the vCon schema. If the JSON
> schema provided below differs from that in the text of the above sections, the
> text should be taken as the definitive definition and the JSON Schema below
> should be consider incorrect.

So: **§1–6 is normative, the appendices are informative, and where they
disagree the prose wins.** That ordering is the reason the next section matters.

## `types.derived.cddl` — how it differs, and which to trust

`types.derived.cddl` is ours. `bin/derive` generated it from
`distilled/fields.yaml`, which is our reading of the prose. It is *not* a
rendering of Appendix C, and the two are not close.

**Trust the source's own schemas.** On every point where `types.derived.cddl`
and the two appendices disagree about whether a parameter is required, the
appendices agree with each other *and* with the prose bullet in §4, and
`types.derived.cddl` is the odd one out. The §4 bullets mark an optional
parameter `(optional)`; a bullet without it is required.

| parameter | §4 prose bullet | Appendix B | Appendix C | `types.derived.cddl` |
|---|---|---|---|---|
| `party.did` (§4.2.6) | `(optional)` | not required | `? did` | **required** |
| `party.civicaddress` (§4.2.9) | `(optional)` | not required | `? civicaddress` | **required** |
| `dialog.duration` (§4.3.3) | `(optional)` | not required | `? duration` | **required**, and typed `any` |
| `dialog.disposition` (§4.3.11) | required for `incomplete` only | `if type=incomplete then required` | only in `dialog_incomplete_type` | **required on every dialog** |
| `attachment.start` (§4.4.2) | required | `required` | `start:` (no `?`) | **optional** |
| `attachment.dialog` (§4.4.4) | required | `required` | `dialog:` (no `?`) | **optional** |
| `attachment.mediatype` (§4.4.5) | conditional | `if body then required` | `? mediatype` | **required** |
| `analysis.type` (§4.5.1) | required | `required` | `type:` (no `?`) | **optional** |
| `analysis.vendor` (§4.5.6) | required | `required` | `vendor:` (no `?`) | **optional** |

Nine named parameters, and `types.derived.cddl` is wrong on all nine — **five by
over-requiring** (`did`, `civicaddress`, `duration`, `disposition`,
`attachment.mediatype`) and **four by under-requiring** (`attachment.start`,
`attachment.dialog`, `analysis.type`, `analysis.vendor`). The fault was in our
`fields.yaml`, and `fields.yaml` has since been corrected on all nine; it is
recorded here rather than silently repaired in place because `bin/derive` output
is never hand-edited. **`types.derived.cddl` is therefore stale, not wrong about
its own inputs** — it is a faithful rendering of a field table that no longer
exists, and the one step left is to re-run `bin/derive`.

Re-running it changes far more than the nine rows, because `fields.yaml` grew as
well as corrected. The file goes from 71 lines and 5 groups to 152 lines and 15.
Ten groups appear for the first time — `party_history`, `redacted`, `amended`
and, with them, the whole of §5: the signed form, `signature`, the JWS header,
the encrypted form, `unprotected`, `recipient` and the JWE header. `dialog`
gains §4.3.10's `body`, `encoding`, `url` and `content_hash` and all six §4.3.14
transfer parameters, which closes the 4.3.9 → 4.3.11 numbering jump; `attachment`
and `analysis` gain the same four Content members. The leaked heading
`"party_history Objects Array"` becomes `"party_history"`, typed
`[* { * tstr => any }]`. `vCon.group`, which exists only in the §6.3.2 registry,
appears. `civicaddress` goes from `any` to `{ * tstr => any }` and `application`
from `any` to `tstr`, and one stale comment — `recordings` annotated
`; §4.3.6 MUST NOT` — becomes `; §4.3.6 MUST`.

Four of the criticisms in the list below are answered by that regeneration and
must be struck when it happens: the missing signed and encrypted forms, the
missing Dialog Content and transfer parameters, the section-numbering jump, and
the leaked heading. The rest stand. Two cosmetic faults arrive with it, both in
`bin/derive` rather than in the field table: object names containing spaces and
parentheses are flattened to `vcon__signed_form_`, `header__jws_` and
`header__jwe_`, and the generator still emits no `extension_parameters_type`.

Beyond optionality, `types.derived.cddl` is structurally much weaker:

- **No signed or encrypted form.** It models §4 only; §5.2 and §5.3 are absent.
- **No extension wildcard.** It omits `extension_parameters_type`, so a strict
  CDDL validator reading it rejects the extension parameters §2.5 permits — the
  opposite of the source's over-permissiveness, and equally wrong.
- **No dialog type discrimination.** It has one flat `dialog` map with
  `"type" => tstr`. The source splits five branches that pin `type` to a literal
  and carry their own parameter sets. Its `MUST NOT` annotations on
  `recordings`, `recording_set`, `session_id`, `message_id`, `mediatype`,
  `parties`, `originator` and `filename` are comments on a single flat map, so
  they no longer say *which* dialog type prohibits what — the information
  Table 1 exists to carry.
- **No §4.3.10 Dialog Content and no §4.3.14 transfer parameters.** `body`,
  `encoding`, `url`, `content_hash`, `transferee`, `transferor`,
  `transfer_target`, `original`, `consultation` and `target_dialog` are all
  missing. Its section numbering jumps 4.3.9 → 4.3.11.
- **Nested objects are opaque.** `redacted`, `amended`, `parties`, `dialog`,
  `analysis` and `attachments` are `{ * tstr => any }`. The source names a type
  for each.
- **No value types.** The source defines `civicaddress_type` (17 GEOPRIV
  fields), `party_history_object_type` with the event choice that pairs
  `keydown`/`keyup` with a required `button`, `session_id_parameter_type` with
  its nested-array form, `dialog_parties_type` with per-channel nesting and
  `null` for an unused channel, `disposition_value_type` as a six-value literal
  choice, and `duration_type = uint / float`. `types.derived.cddl` has none of
  them; its `duration`, `civicaddress`, `parties` and `session_id` are `any`.
- **A leaked heading.** Its last `dialog` member is keyed
  `"party_history Objects Array"` — a section title from §4.3.13 that reached
  the field table as a parameter name. The parameter is `party_history`.

**Reading order, then:** `vcon.schema.json` (or `vcon.derived.schema.json` to
run it) for §4, `types.cddl` for §5 and for the shape of the value types, the
record's requirement set for everything either of them calls advisory, and
`types.derived.cddl` only as a record of what our own field table currently
says — which, on the nine rows above, is not what the draft says.
